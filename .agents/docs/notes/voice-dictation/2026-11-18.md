# Voice dictation integration (2026-11-18)

Scope: shared `pvl` Home Manager profile on Niri, Sway and GNOME Wayland.

- Pin upstream Voxtype, whisrs and Vocalinux flakes; share the existing
  `unstable` nixpkgs input to avoid redundant package-set locks.
- Keep upstream packages/build logic rather than vendoring three applications.
- Default Vulkan for Whisper on AMD/NVIDIA. Expose CPU, whisrs CUDA/HIP,
  Voxtype Whisper ROCm and Voxtype ONNX CUDA/MIGraphX as opt-in builds.
- Provide Voxtype ONNX CPU in parallel with Whisper/Vulkan using a separate
  `voxtype-onnx` command, avoiding two `bin/voxtype` in one profile.
- Enable `hardware.uinput` for Wayland injection, add `pvl` only to the
  `uinput` group, do not grant the broad `input` group.
- Do not enable three concurrent autostarting microphone daemons or assign
  competing desktop hotkeys; users explicitly select a tool.
- Do not claim model/runtime combinations that upstream's Nix packages omit:
  Vocalinux Parakeet extra is absent; Voxtype ONNX has no Vulkan and its
  MIGraphX build has Parakeet acceleration only; whisrs needs a sidecar for
  Parakeet/Cohere.
- whisrs supports phrase-level local Whisper streaming and OpenAI-compatible
  ASR/TTS servers. Ship no unrequested cloud credentials or TTS daemon.

First-use and model/backend matrix: `users/pvl/voice/README.md`.
Verification and any unresolved build issues are recorded in that README or
in the final handoff; no host activation is part of this change.

## GGUF worker correction (2026-11-18)

- Reproduced packaging gap by inspecting Voxtype v1.2.2's pinned flake:
  `packages.vulkan` enables `gpu-vulkan` (which enables `gguf`,
  `parakeet-gguf`, `cohere-gguf`) but installs **no** GGUF worker.
  Selecting a GGUF model therefore fails with `Matching GGUF worker
  'voxtype-gguf-worker' is missing or not executable`.
- Upstream's Dockerfile.vulkan separately builds
  `cargo build -p voxtype-gguf-worker --features vulkan` because
  transcribe.cpp and whisper.cpp have conflicting ggml symbols.
- New `lib/ext/voxtype/gguf-worker.nix` builds the exact pinned upstream
  crate, reusing the upstream flake's Cargo vendor closure. The Vulkan
  package asserts an executable exists and ELF DT_NEEDED contains
  `libvulkan.so.1`.
- `overlays/voice.nix` now composes the appropriate worker with Voxtype,
  sets `VOXTYPE_GGUF_WORKER` only when unset, and also supplies the
  Vulkan worker to separate ONNX command wrappers. The pure CPU variant
  uses a CPU worker. No unconditional daemon or model downloads added.
- Targeted Nix evaluation confirms the worker derivation selects
  `-p voxtype-gguf-worker`, `buildFeatures = vulkan`, and a Vulkan
  library path.
- **Vulkan GGUF worker build passed** on pvl-l5 via
  `nix build --no-link .#nixosConfigurations.pvl-l5.pkgs.voiceTools.voxtype.ggufWorkerVulkan`.
  Native transcribe-cpp-sys compiled and the worker installed at
  `bin/voxtype-gguf-worker`. The ELF post-fixup gate printed
  `NEEDED libvulkan.so.1`. `ldd` resolved the Nix-store Vulkan loader;
  invoking the worker without arguments reached its usage handler (exit
  2, expected for a required-arguments protocol worker).
- The full Voxtype daemon + worker `symlinkJoin` derivation evaluates and
  requires the executable plus a default `VOXTYPE_GGUF_WORKER` pointing
  to the built worker. A full combined-package build and an actual model
  inference test remain distinct qualification steps.
- Worker command protocol tested: `--engine invalid --config-json '{}'`
  returned a structured `config_error` JSON, confirming the executable
  launches and loads its shared libraries. This is not model inference.
- Combined Voxtype Vulkan build attempted twice; the remote build job
  terminated without an exit result during Rust compilation of Voxtype
  itself. No main-binary output was produced. Keep full-package build,
  `voxtype info engines --json`, and actual GGUF transcription as pending
  verification, rather than reporting an end-to-end pass.

## Fleet prepare failures — investigation checkpoint

- Operator reported three `fleet prepare --dirty-staged` failures on pvl-l5,
  with source identities `c21c683b + staged:3e99bae25e23` and
  `c21c683b + staged:6daface845e7` (twice). All stop at the first host
  `pvl-a1`, before the other six hosts are built.
- The configured native Nix builder is **pvl-x2**, even for `build pvl-a1`.
  `host_runtime.rs::run_remote_build` classifies any unsuccessful SSH
  command or missing expected stdout path as `UnconfirmedBuild`. The reported
  `client Exit(1)` does **not** prove a timeout, OOM, or SSH disconnect;
  it is merely the observed SSH process exit. The source deliberately avoids
  an automatic retry of a possibly ongoing remote realization.
- Diagnostics are retained by the manager in
  `/var/tmp/nixbot/diag-<id>/commands/build-pvl-a1-via-pvl-x2.stderr.log`
  with corresponding `.status` and `.stdout.log`. The current Dotlink
  L5 shell grants `/home/pvl/src/nix`, but its Bubblewrap sandbox does
  not mount `/var`; that prevents reading those **existing** diagnostics.
- Checked pvl-x2: Vocalinux and the pinned OpenVINO and Cargo-vendor
  dependencies are realized. Voxtype Vulkan, ONNX, GGUF worker and whisrs
  Vulkan are **not**. Neither host shows a running Nix build after the
  failures. pvl-x2 has around 1.4 TB free and `/proc/vmstat` reports
  `oom_kill 0`; no resource cause is proven.
- Direct builder attempts via Dotlink-x2 reached
  `Compiling transcribe-cpp-sys v0.2.3` but the isolated tool job
  terminated without an exit status before the derivation realized.
  This does not establish a compiler defect. Repeated long-running builds
  under that connector are not an effective end-to-end qualification.
- Nix on the Dotlink sandbox cannot follow the ordinary
  `/etc/ssl/certs/ca-certificates.crt` symlink because `/etc/static`
  is not mounted. An explicit Nix-store `NIX_SSL_CERT_FILE` allowed
  dependency downloads and compilation there. This is a **Dotlink
  sandbox** issue, *not evidence* that the ordinary nixbot SSH session
  has the same certificate defect.
- Source evaluation requests `max-jobs=16, cores=0` on pvl-x2; the
  live Nix client reports `max-jobs=1, cores=0`. This is configuration
  drift, not a diagnosed build failure. The agent-managed durable build
  executor is not enabled in the evaluated NixOS configuration; do not
  switch to `--strategy=agent` without separately qualifying that rollout.
- Voxtype Vulkan, ONNX and whisrs Vulkan have `doCheck=1` in their
  Nix derivations, so a Rust test failure is also possible; no failing
  test evidence was captured.

The retained stderr was copied and inspected in the follow-up below.
Do not diagnose build failures from the activity tail, or automatically
retry an unconfirmed remote realization without settlement evidence.

## Fleet failure resolved to missing Oniguruma build input

The three historical diagnostics were copied into
`tmp/fleet-build-errors/{375f3bf5146b43fdacee1000cf597500,f4231f0b57974aadbafca3b2a6d7a523,e69faff9f47e41779e227ffca912db9b}.stderr.log`.
**All three** show the same first failing derivation:
`077v92aj9pzxrsr656ps88xyp3mwrs84-voxtype-onnx-1.2.2.drv`.
Its `onig_sys-69.9.1` build script exited with Cargo status 101 because
`RUSTONIG_SYSTEM_LIBONIG` is set and `pkg-config oniguruma >= 6.9.3`
failed. The upstream ONNX Nix derivation has `pkg-config` but lacks
`oniguruma` in `buildInputs`. The higher-level Home Manager/system
derivations fail only because they depend on that ONNX build.

Clean fix in `overlays/voice.nix`:

- Keep Voxtype at pinned v1.2.2 and preserve its complete ONNX engine sets.
- Add `pkgs.oniguruma` to the unwrapped ONNX derivation's `buildInputs`
  for CPU, CUDA, and MIGraphX variants.
- Wrap the corrected derivations with the same runtime typing tools,
  `ORT_DYLIB_PATH`, and `LD_LIBRARY_PATH` as upstream, retaining the
  separate GGUF Vulkan worker and MIGraphX model-cache initialization.
- Evaluated the fixed CPU ONNX derivation: its build inputs now include
  `oniguruma-6.9.10-dev`, containing `lib/pkgconfig/oniguruma.pc`, and
  `ORT_LIB_LOCATION` remains set to the exact ONNX Runtime library.
- `pvl-a1`, `pvl-l5`, and `pvl-x2` evaluate with the updated overlay.

Validation: `nix-instantiate --parse` and Alejandra passed; all three
repaired ONNX variants evaluate and the CPU derivation's `buildInputs`
contain `oniguruma-6.9.10-dev/lib/pkgconfig/oniguruma.pc`. A direct
full ONNX build on pvl-l5 was started but the connected tool session
ended without a Nix result, before compilation output began; do **not**
mark that full build qualified. The corrected staged source still
requires realization on a normal builder before fleet deployment.

Further targeted qualification: realized the exact oniguruma `dev`
output and verified `pkg-config --modversion 'oniguruma >= 6.9.3'`
returns `6.9.10`. A subsequent ONNX build progressed through
`Compiling onig_sys v69.9.1`, `Compiling onig v6.5.1`, `tokenizers`,
`parakeet-rs`, and Voxtype compiler warnings without the original
onig build-script failure. The connected job ended without an exit
status before a complete Nix store output; full-package and fleet
realization remain pending.

The fleet's `remote build unconfirmed (client Exit(1))` was a generic
remote-result safety classification; the **diagnostic stderr** proves an
ordinary Nix/Cargo build failure. No SSH/GC/scheduling fixes or changes to
the host-manager's fail-closed realization policy are warranted for this
incident. The older troubleshooting speculation above is superseded by
this evidence. Never retry the old unpatched staged snapshot.

## Review hardening (2026-11-18)

- Removed the broad `input` group; text injection uses `uinput` only.
- The Dotlink source mount `/home/pvl/src/pvl` is provisioned by
  ordinary NixOS tmpfiles on A1/L5/X2 before Dotlink starts. Missing
  declared mounts are not optional in pinned Dotlink v0.17.4.
- Reuse the existing NixOS `ibus-daemon.desktop`: Home Manager's
  per-user XDG override selects `ibus start --type wayland` for
  Niri/Sway. Sway opts into `systemd.xdgAutostart` instead of an
  additional IBus-specific service or compositor `exec`; this also
  enables other eligible XDG autostart applications. GNOME retains its
  separate IBus lifecycle.
- The ONNX fix now replaces only `paths` in each upstream `symlinkJoin`.
  Upstream retains ownership of the full ORT/CUDA/MIGraphX wrappers,
  avoiding drift from copied runtime library lists.
- A1/L5/X2 evaluate with `uinput`, without `input`, and with the IBus
  XDG override. CPU/CUDA/MIGraphX ONNX variants evaluate. Full ASR
  inference and fleet deployment remain untested.
